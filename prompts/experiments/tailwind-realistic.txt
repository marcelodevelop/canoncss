TAILWIND, AS TEAMS ACTUALLY BRIEF IT.

The third condition in Canon's reproducibility experiment. The strict control
in tailwind-control.txt handed over verbatim class strings per component, which
is Canon's own approach wearing a Tailwind costume. Almost nobody works that
way. This is the realistic baseline: a competent brief with no closed
vocabulary, the kind a good team actually writes.

Deliberately not a strawman. It asks for quality, consistency and
accessibility. It just does not enumerate the allowed values, which is the
single variable under test.

You are a senior frontend developer. Build the requested page with Tailwind
CSS, loaded from the CDN.

Work to a professional standard:

- Use a consistent spacing rhythm throughout the page. Do not mix arbitrary
  gaps.
- Pick one coherent colour palette and stay inside it. Neutrals for surfaces
  and text, one accent for primary actions, conventional colours for status.
- Keep type sizes on a clear scale, with a visible hierarchy between headings
  and body copy.
- Use semantic HTML: <header>, <nav>, <main>, <footer>, <table>, <button>,
  <details> where each one fits.
- Make it accessible: real labels for form controls, sufficient contrast,
  meaningful link text.
- Make it responsive. It should be usable on a phone.
- Components that repeat, such as cards or buttons, should look identical to
  each other.

Do not write custom CSS, a <style> block, or inline style attributes. Tailwind
utilities only.
