Why We Rewrote Our Event Pipeline in Rust

How we cut p99 latency by 87% and stopped paging the on-call engineer at 3 a.m.

Mira Castellanos, Staff Engineer July 28, 2026 · 11 min read

Eighteen months ago, our event pipeline was a Node.js service that had grown by accretion. It ingested roughly 40,000 events per second at peak, fanned them out to a dozen downstream consumers, and did so with a p99 latency that we described internally as "aspirational." Every Black Friday it fell over, and every Black Friday we added another cache in front of it.

This is the story of how we replaced it with a Rust service, what we got wrong along the way, and the numbers that convinced a skeptical leadership team that a rewrite — the most dangerous project in software engineering — was actually the conservative choice.

"A rewrite is not a bet on a new language. It is a bet that you finally understand the problem you were solving all along."

The symptoms we could no longer ignore

The old pipeline was not slow because Node.js is slow. It was slow because the architecture forced every event through a single serialization boundary, and garbage collection pauses stacked up behind it. By the time we committed to the rewrite, we had a list of symptoms that no amount of tuning had fixed:

  • GC pauses of 300–800 ms during peak traffic, which blew our 250 ms latency budget on their own.
  • Backpressure that propagated upstream unpredictably, causing producers to buffer and occasionally drop events.
  • Memory usage that grew roughly linearly with connected consumers, capping horizontal scale.
  • A serialization layer (JSON.parse on every hop) that consumed 40% of total CPU time in flame graphs.
  • An on-call rotation where "restart the pipeline" was the documented first response to five separate alert types.

What we measured before writing a line of Rust

Before touching the new codebase we spent three weeks instrumenting the old one. The rule was simple: no claim about the rewrite would be accepted without a baseline number from production. We captured throughput, tail latency, memory ceilings, and — critically — the cost per billion events, because infrastructure spend was the argument leadership actually cared about.

Comparison of the legacy Node.js pipeline and the new Rust pipeline
Metric Node.js (legacy) Rust (new)
p99 latency 412 ms 53 ms
Peak throughput per node 11,000 events/s 96,000 events/s
Memory at peak 6.2 GB 410 MB
Cost per billion events $184 $23

How we migrated without a big-bang cutover

The rewrite shipped incrementally over four months. Nothing here is novel — it is the strangler-fig pattern applied with discipline — but the ordering mattered more than we expected:

  1. Mirror production traffic to the new service in shadow mode, discarding its output.
  2. Diff the shadow output against the legacy output for two weeks and fix every divergence, however small.
  3. Route 1% of real consumers to the new pipeline behind a feature flag, then 10%, then 50%.
  4. Run both pipelines at 100% in parallel for one full weekly traffic cycle, including a load-test day.
  5. Decommission the legacy service — and delete the code, so nobody could quietly route back to it.

The shadow-mode diffing in step two was where the real work happened. We found eleven behavioral differences, and nine of them were bugs in the old pipeline that consumers had silently learned to tolerate. Deciding whether to preserve or fix each one was a product decision, not an engineering one.

Reproducing the benchmark yourself

We open-sourced the load harness. If you want to reproduce the throughput numbers on your own hardware, the whole run is one command: 

cargo run --release -p ledger-bench -- \
  --events 10000000 \
  --consumers 12 \
  --payload-size 2kb \
  --report json > results.json

The harness spins up an in-process broker, so the numbers isolate the pipeline itself from network variance. Pass --report human instead of --report json for a readable summary, and use --consumers to match your production fan-out. On an 8-core machine you should see results within about 10% of ours.

What we would do differently

The rewrite succeeded, but not because Rust is magic. It succeeded because we spent three weeks measuring before we spent four months building, because shadow mode caught the bugs a test suite never would have, and because we deleted the old code instead of leaving it as a comfort blanket. The borrow checker was the easiest part. If your pipeline is falling over, start with the flame graph — the language decision comes last.
