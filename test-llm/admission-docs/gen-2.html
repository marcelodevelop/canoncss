GET Deprecated Retires 1 March 2027

GET /v2/shipments

Returns a paginated list of shipments belonging to the authenticated account, newest first. Use it to reconcile your own records against Northwind, to poll for shipments whose status changed since your last sync, or to page through a carrier's backlog. It reads only: it never creates, books or cancels a shipment.

Deprecated endpoint This endpoint is being retired. Migrate to /v3/shipments.
1 March 2027 Last day GET /v2/shipments answers requests

After that date every call to /v2/shipments returns 410 Gone. There is no grace period and no extension for individual accounts. From 1 September 2026 the endpoint also begins returning a Sunset response header on every call.

The replacement, GET /v3/shipments, accepts the same filters plus cursor pagination on every collection. The response envelope changed: data replaces shipments, and timestamps are RFC 3339 with an explicit offset.

Read GET /v3/shipments Migration guide

Query parameters

All parameters are optional unless marked required. Unknown parameters are rejected with 400 invalid_parameter.

Name Type Required Description
account_id string Required The account whose shipments are returned. Must be an account your API key can read, otherwise the call fails with 403.
status string Optional Filter by lifecycle state: draft, booked, in_transit, delivered, cancelled. Repeat the parameter to pass more than one value.
updated_since string (ISO 8601) Optional Return only shipments modified at or after this instant. Values older than 400 days are clamped to the retention window.
carrier_code string Optional Restrict results to a single carrier, for example dhl_express. See the Carriers section for the full list of codes.
limit integer Optional Number of shipments per page, 1 to 100. Defaults to 25.
page integer Optional Offset page number, starting at 1. Offset paging is the v2 behaviour; v3 uses an opaque cursor instead.

Common questions

Can I keep calling /v2/shipments after 1 March 2027?

No. The route is removed, not frozen. Every request after that date returns 410 Gone with an error body pointing at /v3/shipments. Pinning an older SDK version does not help, because the retirement happens server side.

Why does total sometimes change between pages?

total is counted at the moment each page is served, so a shipment created or cancelled mid-walk shifts it. If you need a stable walk, filter with updated_since and treat the run as incremental rather than as a snapshot. The v3 endpoint solves this with cursor pagination, where a cursor stays valid for 24 hours.

How do I fetch shipments across several accounts?

One call per account. account_id takes a single value and cannot be repeated. Calls are rate limited per API key, not per account, at 600 requests per minute, so fan out with a small amount of concurrency and honour the Retry-After header on 429.

Are cancelled shipments included by default?

Yes. With no status filter the response contains every lifecycle state, including cancelled and draft. Pass the states you want explicitly if your reconciliation job should ignore them.
