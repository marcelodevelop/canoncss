GET

/v2/shipments

List shipments for the authenticated account, newest first.

Deprecated This endpoint is being retired. Migrate to /v3/shipments.
1 March 2027 Last day GET /v2/shipments answers requests

After that date every call to /v2/shipments returns 410 Gone. /v3/shipments is available today and accepts the same filters, with two differences: cursor pagination replaces page, and status accepts multiple values. Nothing else in the request changes.

Read the v3 reference Migration guide

What it does

Returns a paginated list of shipment records belonging to your account. Each record carries the carrier, the current status, the origin and destination warehouses, and the last scan event. Use the query parameters below to narrow the list by carrier, status, or creation window. Results are ordered by created_at descending and are scoped to the API key's organisation, so a key issued to one business unit never sees another's freight.

Query parameters

Name Type Required Description
carrier_id string Optional Return only shipments tendered to this carrier. Accepts a carrier ID such as car_9f2c.
status string Optional One of draft, tendered, in_transit, delivered, exception. v2 accepts a single value only.
created_after string Optional ISO 8601 timestamp. Only shipments created at or after this instant are returned.
warehouse_id string Required Origin warehouse to list from. Required since v2.4; calls without it return 400.
page integer Optional 1-based page number. Defaults to 1. Replaced by cursor in v3.
limit integer Optional Records per page, between 1 and 200. Defaults to 50.

Common questions

Why do I get a 400 when I omit warehouse_id?

Since v2.4 the origin warehouse is mandatory, because unscoped listing was timing out for accounts with more than a hundred thousand shipments. Loop over the warehouses returned by GET /v2/warehouses and issue one call per warehouse, or move to /v3/shipments, where the filter is optional again.

Can I filter by more than one status at a time?

Not on v2. status takes a single value here, and passing a comma separated list matches nothing rather than erroring. On /v3/shipments the parameter repeats: ?status=in_transit&status=exception.

What happens to my integration on 1 March 2027?

Requests stop being served and return 410 Gone with an error body pointing at the v3 path. There is no grace period and no extension by request. From 1 December 2026 responses also carry a Sunset header so you can alert on it before the cutoff.
