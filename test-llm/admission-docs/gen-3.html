What this endpoint does

Returns a paginated list of shipments belonging to the authenticated account, newest first. Use it to reconcile your own records against Northwind, to poll for shipments whose status changed since your last sync, or to build an operations dashboard. A single shipment is better fetched by ID; this endpoint is for ranges and filters.

Requires the shipments:read scope. Rate limited to 120 requests per minute per API key.

Query parameters

Name Type Required Description
status string Optional Filter by lifecycle state. One of draft, booked, in_transit, delivered, cancelled. Repeat the parameter to match several states.
carrier string Optional Carrier slug, for example dhl-express. Unknown slugs return an empty list rather than an error.
updated_since string (RFC 3339) Required Only return shipments updated at or after this timestamp. Required so that unbounded scans cannot be issued by accident. Maximum window is 90 days.
destination_country string (ISO 3166-1 alpha-2) Optional Two-letter destination country code, for example NL. Case insensitive.
limit integer Optional Page size, between 1 and 200. Defaults to 50.
page integer Deprecated One-based page offset. Removed in v3, which uses cursor instead. Ignored when cursor is also supplied.

Common questions

Why does an empty updated_since return 400?

updated_since is the one required parameter. Without it a caller can ask for every shipment ever created, which times out on large accounts. Send the timestamp of your last successful sync. If you have no previous sync, start 90 days back and walk forward in windows.

Is the list ordered, and is the order stable across pages?

Results are ordered by updated_at descending. The order is not stable while shipments are being updated underneath you, so a shipment can move between pages during a long offset-paged scan. This is one of the reasons v3 replaces page with a cursor. If you must stay on v2, de-duplicate by id as you read.

What actually changes when I move to /v3/shipments?

The filters keep their names. Three things change in the response and paging contract:

  1. results becomes data.
  2. page and total are gone; use cursor and the next_cursor field.
  3. carrier expects a carrier ID such as car_19Ka, resolvable from the carriers endpoint.
