GET https://api.northwind.com/v2/shipments

List shipments

Deprecated This endpoint is retired on 1 March 2027

After 1 March 2027 any call to GET /v2/shipments returns 410 Gone. There is no grace period and no extension for individual accounts. Move every caller to GET /v3/shipments before that date.

From 1 September 2026 responses also carry a Sunset header and a Deprecation: true header so you can find the remaining callers in your own logs.

Read the v3 reference v2 to v3 migration guide

Returns a cursor-paginated list of shipments belonging to your organisation, newest first. Use the query parameters below to narrow the list by carrier, lifecycle status, origin warehouse or update time. Shipments deleted more than 90 days ago are not returned.

Requires an API key with the shipments:read scope. Rate limited to 120 requests per minute per organisation.

Query parameters

Name Type Required Description
account_id string Required Identifier of the billing account whose shipments you want. Must be an account your key can read.
status string Optional Filter by lifecycle status: draft, booked, in_transit, delivered or cancelled. Repeat the parameter to pass several.
carrier_code string Optional Restrict results to one carrier, for example dhl_express. See the carriers reference for the full list.
updated_after string (RFC 3339) Optional Only return shipments changed strictly after this timestamp. Use this to poll for changes instead of refetching everything.
limit integer Optional Page size between 1 and 200. Defaults to 25.
cursor string Optional Opaque cursor taken from next_cursor on the previous page. Do not construct one yourself.

Common questions

Why do I get fewer results than the limit I asked for?

A page can come back short and still have more results behind it. Filtering happens after the page is read, so the only reliable signal is has_more. Keep following next_cursor until has_more is false, and never treat a short page as the end of the list.

Can I keep calling /v2/shipments after 1 March 2027?

No. On that date the route stops serving data and answers 410 Gone for every caller, including keys that have been calling it for years. The replacement is GET /v3/shipments, which keeps the same cursor pagination but renames weight_grams to weight.value plus weight.unit and drops the top-level tracking_number in favour of the tracking resource.

See the field-by-field migration table

How do I poll for shipments that changed since my last sync?

Store the highest updated_at you have seen and pass it back as updated_after on the next run. Subtract a minute of overlap to absorb clock skew between regions, then de-duplicate by id on your side. Polling more often than once a minute will hit the rate limit before it gains you anything, so prefer shipment webhooks if you need faster updates.
