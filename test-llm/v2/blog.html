Why We Moved Our Event Pipeline to Append-Only Logs

MA

Marcela Andrade

Staff Engineer, Platform · Published July 28, 2026 · 9 min read

Eighteen months ago, our event pipeline was a tangle of queues, cron jobs, and a shared Postgres table that everyone was afraid to touch. Events were mutated in place, consumers stepped on each other, and every incident review ended with the same sentence: "we can't reconstruct what actually happened." This is the story of how we replaced all of it with a single append-only log, and what we learned along the way.

The core insight is not new. Databases have been built on write-ahead logs for decades, and systems like Kafka turned the log itself into the product. What was new for us was committing to the discipline: no updates, no deletes, no status column that flips from pending to processed. Every fact that enters the system stays exactly as it was written, forever.

The problem with mutable state

Our old pipeline stored events in a table and updated rows as they moved through processing stages. It worked at small scale, but as we grew we kept hitting the same categories of failure:

  • Lost history. Once a row was updated, the previous state was gone. Debugging a mis-processed event meant guessing.
  • Consumer coupling. Two services reading the same table had to coordinate locks, which meant they had to know about each other.
  • Impossible replays. Backfilling a new downstream service required a bespoke migration script every single time.
  • Write contention. Status updates and new inserts fought over the same hot pages, and vacuum churn degraded every query in the database.
  • Audit gaps. Compliance asked "who changed this and when," and our honest answer was a shrug.

An update is a fact that destroys another fact. An append is a fact that respects the ones that came before it.

How the migration actually worked

We did not rewrite the pipeline in one heroic quarter. We ran the old and new systems side by side and moved consumers over one at a time. The sequence that worked for us:

  1. Introduce the log as a shadow write: every mutation to the old table also emits an immutable event.
  2. Verify parity with a differ that replays the log and compares the result against the live table, row by row.
  3. Migrate read-only consumers first, since they can fall back to the old table instantly if something looks wrong.
  4. Migrate writers, flipping each one behind a feature flag with a one-command rollback.
  5. Freeze the old table, keep it for ninety days as a safety net, then archive it to cold storage.

Bootstrapping a local replica

One underrated benefit: any engineer can now rebuild the entire derived state on a laptop. The ledgerctl CLI streams the log from the first offset and applies it to a local materialized view: 

$ ledgerctl replay --from-offset 0 --topic orders.v2 --target sqlite://local.db
replaying 4,218,067 events... done in 3m12s (21,970 events/s)

Because the log is the source of truth, the local replica is not a fixture or a mock — it is bit-for-bit the same state production would compute. When someone reports a bug at offset 1883412, you replay to that offset and you are standing exactly where production stood.

What it cost us

Append-only is not free. Storage grows monotonically, so we compact aged segments into snapshots. Reads that used to be a single indexed lookup are now served from materialized views that must be kept fresh. And every engineer had to unlearn the reflex of reaching for UPDATE. Here is how the two architectures compare on the dimensions we cared about most:

Dimension Mutable table (before) Append-only log (after)
Debugging an incident Reconstruct from partial logs and guesswork Replay the exact event sequence to any offset
Adding a new consumer Custom backfill script, days of work Subscribe from offset zero, hours of work
Write throughput (p99) ~1,200 events/s before lock contention ~48,000 events/s, sequential appends
Storage cost per month Low, but history is destroyed Higher, mitigated by segment compaction

Would we do it again? Without hesitation. The pipeline has been in production for a year, has survived two region failovers, and — for the first time in the company's history — every incident review starts from a complete, ordered, immutable record of what happened. The log does not lie, and it turns out that is worth paying for.
